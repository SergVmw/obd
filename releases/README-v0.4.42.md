# Release 0.4.42 — 2026-10-26

Поездка, которая не закрывается, теперь закрывается.

`0.4.41` добавила в дамп числа, по которым это видно; этот выпуск закрывает
причину, которую они показали. Правка одна и в одном месте — в автомате границ
поездки. Опрос, готовность мониторов, расчёт топлива, коды и запись истории не
тронуты.

---

## 2. Почему закрытие не могло сработать

Закрытие по стоянке — это одно сравнение:

```cpp
(rtcNowSec - parkedSinceRtcSec_) >= tripGapMin * 60
```

`parkedSinceRtcSec_` переживает цикл питания: он лежит в NVS и приезжает через
`seedRecoveredOpenTrip()`, храня момент, когда двигатель работал **в прошлой
жизни прибора**. `currentRtcSec()` — счётчик RTC (`esp_clk_rtc_time()`), и при
подаче питания он начинается заново. Сохранённый якорь оказывается впереди
живого счёта, `rtcNowSec >= parkedSinceRtcSec_` не выполняется никогда — ни через
пять минут, ни через семнадцать часов, — окно стоянки не истекает, и поездка
остаётся открытой.

Выхода из этого состояния нет, пока машина стоит: `parkedSinceRtcSec_`
перезаписывается только при открытии **нового** окна, а новое окно открывается
только после движения.

Кламп в `TripContextStore::begin()` эту полосу не закрывает. Он откатывает метки
только когда `rtcNowSec < startRtcSec`. Метка старта поездки — это секунды от
подачи питания до первого `RPM`, то есть единицы секунд; метка текущей
загрузки — тоже единицы секунд. Полоса `startRtcSec <= rtcNowSec <
lastActiveRtcSec` — ровно тот случай, когда кламп молчит, а якорь уже впереди.
Разница в дампе (`3 051` с между стартом поездки и загрузкой) — это она и есть.

## 3. Что изменено

`src/trip_boundary.cpp`, начало `TripBoundary::update()`:

```cpp
if (inParkedWindow_ && parkedSinceRtcSec_ > rtcNowSec) {
  parkedSinceRtcSec_ = rtcNowSec;
  gapCheckedThisWindow_ = false;
}
```

Первый тик, увидевший якорь впереди живого счёта, переносит якорь на текущий
момент. Прошедшее время паузы по часам, ушедшим назад, измерить нельзя, поэтому
оно честно ноль — и окно отрабатывает свои `tripGapMin` как любое другое.

Правка в автомате, а не в вызывающем коде, потому что вызывающих два (`setup()`
и `loop()`) и любой из них может засеять якорь снова. Инвариант «окно не может
быть неистекаемым» держится в одном месте.

Длительность записи от правки не портится: `buildRecord()` берёт
`endRtcSec = lastActiveRtcSec`, то есть конец работы двигателя, а не момент
закрытия. Закрытие через пять минут после загрузки даёт запись с честным
интервалом работы.

## 4. Чем это закрыто

`testBoundarySnapshotReportsTheCloseArithmetic` падал на старом коде ровно на
`parkedSinceRtcSec == 901`: засев `9000` при живом счёте `901` не переякоривался.
Теперь он проверяет три вещи:

* якорь из прошлой жизни переякоривается первым же тиком, и поездка закрывается
  ровно на `901 + 300`;
* короткий заезд (`45` м) в том же состоянии по-прежнему не закрывается и уходит
  в слияние — правило `tripMinDistanceM` сильнее починки часов;
* нормальный посев без отката часов ведёт себя как раньше.

Обратная проверка по объектному коду. `trip_boundary.cpp.o` для
`esp32s3_n16r8`: `671` байт `.text` без блока, `704` с блоком. `main.cpp.o`:
`17 374` без вызова в сервисной ветке, `17 398` с ним. После восстановления
файлов SHA-256 приложения совпал побайтово (`e189e519…`), то есть обе правки
действительно в образе, а сборка воспроизводима.

## 7. Второе изменение: поездка и сервисный режим

Та же тема с другого конца. `loop()` в сервисном режиме выходит по `return` до
того места, где обновляются границы поездки, поэтому пока портал открыт,
поездка не растёт и не закрывается, а двигатель для границ невидим (в дампе
`rpm` `778` при `serviceMode: true`). Таймаут сервисного режима заменой не был:
он считается от `lastActivityAt_`, а `touch()` вызывается на каждый HTTP-запрос,
включая собственный опрос страницы раз в `1.2` с, — открытая вкладка держит
сервисный режим сколько угодно, и 15 минут не наступают никогда.

Теперь границы считаются в обоих режимах одной функцией:

```cpp
void updateTripBoundary(uint32_t now, uint32_t rtcSec) {
  if (tripBoundary.update(rtcSec, telemetry.rpm.valid(now),
                          telemetry.rpm.value, telemetry.rawSpeedKph.valid(now),
                          telemetry.rawSpeedKph.value, trip.totalDistanceKm,
                          configStore.data().tripGapMin,
                          configStore.data().tripMinDistanceM) !=
      TripBoundaryAction::None) {
    closeOpenTripToHistory(now, rtcSec);
  }
}
```

Вызывающих три: `setup()` (после засева открытой поездки), обычный путь `loop()`
и сервисная ветка перед `servicePortal.loop()`. В сервисном режиме опрос OBD
остаётся активным, поэтому `rpm` и `rawSpeedKph` там живые — границам больше
ничего и не нужно.

Как это ощущается:

* приехал, двигатель работает, открыл портал, смотришь — поездка не закрывается,
  потому что двигатель работает;
* заглушил двигатель, не выходя из сервиса, — через `tripGapMin` поездка
  закрывается сама, карточка появляется в истории, панель текущей поездки в
  портале обнуляется;
* вышел из сервиса и заглушил — закрывается на стоянке, как раньше.

Цена: топливо и секунды простоя в сервисном режиме по-прежнему не накапливаются
(там работает `refreshLiveTelemetry()`, а не `update()`). Поездка, закрытая после
получаса в сервисе с работающим мотором, недосчитает этот простой. Расход в
сервисном режиме недостоверен, а закрытие — достоверно и не должно от него
зависеть.

Правило записано в `docs/TRIP_HISTORY_DESIGN.md` §3.6. Гейт
`check_trip_history_integration.py` проверяет форму, а не строку: одно место
вызова `tripBoundary.update(` в файле, три вызывающих `updateTripBoundary(`, и
то, что в сервисной ветке вызов стоит до `return`.
