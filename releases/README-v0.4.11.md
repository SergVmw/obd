# H2 Gauge 0.4.11

Поверх 0.4.10, который остаётся нетронутым и доступен по метке `v0.4.10`.

В релизе три независимые правки. Две из них вызваны одними и теми же
данными — полевым отчётом, который впервые удалось снять, потому что 0.4.10
починил перезагрузку на вкладке «Диагностика».

## 1. Разбор DTC сдвинут на байт счётчика

Отчёт с машины дал то, чего ждали с 0.4.9:

```
stored    : 43 00
pending   : 47 00
permanent : None   (Mode 0A отклонён, NRC 0x11 — verdict unsupported, верно)
```

`43 00` — это не повреждённый ответ. Пара DTC занимает два байта, поэтому
единственный байт за эхом сервиса половиной пары быть не может: это счётчик
кодов, и он равен нулю.

Парсер вычитал только эхо сервиса, из-за чего счётчик оставался первым байтом
кода, а проверка чётности работала по нечётной длине. Стандартный ответ всегда
чётной длины, значит `длина − 1` всегда нечётно:

| кодов | ответ | длина | dtcBytes | вердикт |
|---|---|---|---|---|
| 0 | `43 00` | 2 | 1 | malformed |
| 1 | `43 01 AA BB` | 4 | 3 | malformed |
| 2 | `43 02 AA BB …` | 6 | 5 | malformed |

**На любой правильный ответ ставился вердикт «повреждённый ответ».**

Последствие было не косметическим. `scanStatusUsableForClear()` принимает
только `Complete` или `Unsupported`, а эта машина отвечает и по сохранённым, и
по ожидающим как `Malformed`. Предварительное чтение перед очисткой не проходило
никогда, и кнопка очистки отказывала с `preclear_scan_failed` при том, что
блок не сообщал ни одной неисправности. Функция была недостижима, а не сломана.

Счётчик принимается, только когда арифметика сходится — `объявленное × 2` равно
числу байт за ним. Блок, отвечающий без счётчика, по-прежнему разбирается
прежним путём.

`check_dtc_integration.py` искал буквальную строку `size_t dtcBytes = length - 1U;`
— то есть закреплял именно неправильную форму и препятствовал починке этого
класса дефектов. Теперь закрепляет арифметику и порядок «сырые байты снимаются
до оценки длины».

## 2. Имена PID расходились со стандартом

Подписи в отчёте о блоках брались из таблицы, которая была неверна примерно на
`0x1D..0x4D`: там стояли кислородные нагреватели и мониторы OBD, которые живут
по другим PID. Две первые записи были сдвинуты в сторону, которая стоила
больше всего:

| PID | было | по SAE J1979 |
|---|---|---|
| 0x03 | Calculated engine load | **Fuel system status** (битовое поле) |
| 0x04 | Measured air flow (MAF) | **Calculated engine load** |

Это не косметика. Подпись `0x04 = Measured air flow` увела проверку в сторону
датчика воздушного потока, которого на машине нет: `0x10` не поддерживается.
Пришлось откатиться, когда выяснилось, что 0x04 — это расчётная нагрузка,
которую блок выводит сам.

Таблица переписана по SAE J1979 Service 01, 96 записей. Новый гейт
`tools/check_pid_names.py` закрепляет каждую запись и отдельно повторяет
нагрузочные PID, чтобы падение называло последствие.

Значения при этом не затронуты: они считаются по номеру PID, а не по подписи.

## 3. Профиль опроса: 0x44 убран, 0x04 добавлен

`0x44` (эквивалентное отношение) убран из профиля. На этой машине его нет в
маске поддержки, так что запрос и раньше не уходил на шину. Единственное, что
он давал, — `phi` в модели топлива; для калибровки VE честнее теоретическая
масса воздуха, а `phi` несёт обогащение, выбранное блоком, то есть не ту
величину, которая калибруется.

`0x04` (расчётная нагрузка) добавлен с интервалом 1000 мс. На машине без датчика
воздушного потока блок выводит эту величину сам, из давления и оборотов, —
ровно то, против чего имеет смысл сверять нашу скоростную плотность вместо
заправки по счётчику. В статус добавлено поле `engineLoadPct`.

Удаление `0x44` меняет модель топлива для любой машины, которая на него
отвечает: `phi` становится 1.0. Для бензина это правильное значение.

`0x33` (барометр) оставлен. Планировщик не отправляет PID, которых нет в маске,
поэтому `baroKpa: null` ничего не доказывает — блок может отвечать на 0133,
просто не анонсируя его. Вопрос закрывается проверкой снаружи прибора; отдельная
прошивка ради диагностики не делалась.

## Что проверить на машине

1. Вкладка «Диагностика» → сканирование DTC. «Сохранённые» и «ожидающие» должны
   показать **OK** вместо «повреждённый ответ». Это главная проверка релиза.
2. Кнопка очистки ошибок больше не должна отказывать «предварительное чтение DTC
   неполное». Без ошибок очистка не нужна — важно, что она перестала быть
   недостижимой.
3. Отчёт о блоках: имена PID теперь соответствуют стандарту. `0x03` — статус
   топливной системы, `0x04` — расчётная нагрузка, `0x33` — барометр.
4. В статусе появилось `engineLoadPct`. Рядом с `speedDensityAirflowGps` это
   даёт пару для сверки VE без заправки по счётчику.
