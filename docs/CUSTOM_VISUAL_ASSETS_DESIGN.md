# Пользовательские фон и стартовый логотип — архитектура 0.3.9

**Статус:** реализовано и покрыто локальными host/static/browser gates в кандидате 0.3.9; физическая проверка на N16R8 ещё требуется. Уже упакованные бинарники OTA-hardening 0.3.8 не переписывались.  
**Цель:** оставить встроенные фон/логотип безусловным fallback, но разрешить загрузить пользовательские варианты через локальный web-сервис.

## Краткий вывод

Функция реализована для N16R8 без постоянного чтения LittleFS в render loop:

1. хранить пользовательские ресурсы в существующем разделе LittleFS;
2. в браузере привести картинку к окончательному размеру и RGB565;
3. прочитать фон из LittleFS только один раз при старте в уже существующий PSRAM background cache;
4. никогда не читать фон из файловой системы на каждом кадре;
5. загружать новый ресурс во временный/A-B файл, проверять CRC и только затем делать его активным;
6. при любой ошибке использовать встроенные procedural carbon и HAVAL logo.

При штатном app-only web OTA ресурсы находятся вне обоих app slots и поэтому по разметке не затрагиваются. Их сохранение — не вероятностный эффект, а свойство границ разделов.

## Текущие ресурсы и память

Сейчас:

- фон 240×240 генерируется `DashboardUi::drawCarbonBackground()`;
- готовый фон один раз помещается в существующий 16-bit PSRAM cache;
- размер background cache: `240 × 240 × 2 = 115 200` байт;
- каждый кадр восстанавливает его одним `memcpy()` в основной framebuffer;
- встроенный HAVAL logo: 216×38 RGB565;
- размер его реальных пикселей: `216 × 38 × 2 = 16 416` байт;
- fade занимает 18 кадров / 1,5 секунды, общая заставка — 2 секунды;
- в RAM при текущем варианте логотипа держится только scanline 432 байта.

N16R8 имеет 8 МБ PSRAM. Уже работающие штатные буферы:

```text
main RGB565 framebuffer     115 200 bytes
background RGB565 cache     115 200 bytes
smooth text layers           48 960 bytes
```

Пользовательский фон может занять существующий background cache — дополнительный постоянный PSRAM для него не нужен.

## Существующая разметка Flash

```text
nvs       0x009000  0x005000
otadata   0x00E000  0x002000
app0      0x010000  0x400000
app1      0x410000  0x400000
coredump  0x810000  0x010000
littlefs  0x820000  0x7E0000
```

LittleFS имеет `0x7E0000 = 8 257 536` байт, то есть 7,875 МиБ. Проект уже резервирует этот раздел, но текущая прошивка его не использует.

### Оценка места

Фон без сжатия:

```text
240 × 240 RGB565 = 115 200 bytes
```

Текущий размер логотипа:

```text
216 × 38 RGB565 = 16 416 bytes
```

Более гибкий рекомендуемый canvas логотипа:

```text
220 × 80 RGB565 = 35 200 bytes
```

Даже при двух копиях A/B для атомарного обновления:

```text
2 × (115 200 + 35 200) = 300 800 bytes
```

Это примерно 3,64% существующего LittleFS. Сжимать такие данные ради места не требуется.

## Рекомендуемый формат

Не следует загружать PNG/JPEG и декодировать его на ESP32 при каждом старте. Это добавит decoder, heap pressure, неопределённое время декодирования и дополнительные пути отказа.

Рекомендуемый процесс:

1. пользователь выбирает PNG/JPEG/WebP в обычном браузере;
2. JavaScript Canvas показывает preview, кадрирует и масштабирует изображение;
3. фон приводится ровно к 240×240;
4. логотип вписывается с сохранением пропорций в canvas не больше 220×80;
5. прозрачность логотипа смешивается с штатным тёмным фоном;
6. яркость/контраст фона регулируются до передачи, чтобы цифры оставались читаемыми;
7. браузер преобразует результат в RGB565;
8. ESP получает маленький бинарный H2 asset с заголовком и пикселями.

Пример заголовка:

```text
magic
formatVersion
assetType (background/logo)
width
height
pixelFormat (RGB565)
payloadBytes
generation
CRC32
```

ESP не должен парсить SVG и не должен доверять filename. Он принимает только точные размеры, pixel format, длину и CRC.

## Передача через web

Известный блокирующий multipart parser возвращать нельзя. Для ресурсов нужен тот же безопасный принцип, что для firmware:

```http
POST /api/assets/background
Content-Type: application/octet-stream
X-H2G-Action: asset-background
```

и отдельно:

```http
POST /api/assets/logo
Content-Type: application/octet-stream
X-H2G-Action: asset-logo
```

Перед binary body желательно выполнять preflight с типом, размерами, длиной и CRC. Сервер ограничивает тело точным максимально допустимым размером, кормит TWDT, имеет idle/absolute timeout и не разрешает asset upload одновременно с OTA.

Web UI должен предоставлять:

- preview 240×240 с реальными шкалой и текстом;
- crop/fit;
- затемнение фона;
- «Использовать пользовательский»;
- «Временно использовать встроенный» без удаления файла;
- «Удалить пользовательский фон/логотип»;
- состояние CRC/версии ресурса;
- явное предупреждение, что слишком светлый фон ухудшит читаемость.

## Атомарное сохранение

Простая перезапись активного файла опасна при потере питания. Рекомендуется A/B схема:

```text
/assets/background.a
/assets/background.b
/assets/logo.a
/assets/logo.b
/assets/manifest.a
/assets/manifest.b
```

Порядок обновления:

1. определить неактивный bank;
2. записать новый файл туда;
3. `flush()` и `close()`;
4. открыть файл повторно и проверить header, размер и CRC;
5. записать новый manifest generation в неактивную копию;
6. проверить manifest;
7. считать generation с валидным CRC активным;
8. старую рабочую копию пока не удалять.

При потере питания новая загрузка может не активироваться, но прежний рабочий ресурс остаётся. При повреждении обеих копий используется встроенный default.

LittleFS нельзя монтировать через безусловный `LittleFS.begin(true)`: автоматическое format-on-fail способно уничтожить ресурсы после временной ошибки mount. Нужны:

- mount без автоформатирования;
- отдельное безопасное создание файловой системы на действительно пустом разделе;
- ручная подтверждаемая команда repair/format;
- fallback на встроенные ресурсы при любом отказе.

## Производительность

### Постоянная работа прибора

Если custom background один раз загружен в существующий `backgroundCache_`, дальнейший путь кадра остаётся тем же:

```text
PSRAM background cache -> memcpy 115 200 bytes -> main framebuffer
```

Ожидаемое снижение steady-state FPS: практически 0%; разница должна находиться около погрешности измерения. Smooth Golos layers продолжат смешиваться с фактическими пикселями фона.

Категорически нельзя читать 115 200 байт из LittleFS на каждом кадре. При 10–20 FPS это создало бы 1,15–2,30 МБ/с файлового трафика плюс latency и заметные stalls.

### Старт

Оценка до аппаратного benchmark:

| Операция | Ориентировочный эффект |
|---|---:|
| mount LittleFS | примерно 10–100 мс |
| read + CRC фона 115 200 байт | примерно 10–50 мс |
| read + CRC логотипа 16–35 КБ | примерно 2–20 мс |
| копирование фона в уже существующий cache | включено в чтение |
| основной render после старта | без постоянного штрафа |

Итого ожидаемое дополнительное время cold start — обычно менее 0,2 секунды. Это оценка, а не аппаратно измеренный результат.

### Анимация логотипа

Текущий logo — 8 208 пикселей на кадр. Canvas 220×80 — 17 600 пикселей, то есть примерно в 2,14 раза больше работы fade. Но анимация уже специально растянута на 1,5 секунды и содержит ожидание между 18 кадрами, поэтому такой размер должен помещаться в текущий временной бюджет.

Варианты:

- минимум PSRAM: читать/держать один scanline 440–480 байт;
- меньше файловых операций: один раз загрузить logo в PSRAM, дополнительный расход до 35 200 байт;
- full-screen animated splash 240×240 нежелателен: он заметно увеличит объём SPI на каждом fade frame без пользы для обычного логотипа.

Если PSRAM недоступна, custom background лучше не читать каждый кадр, а автоматически использовать procedural default. Это сохраняет нынешний аварийный 8-bit путь.

## Сохранение при обновлениях

### Штатный web OTA обычного app `.bin`

Ожидаемое сохранение: 100% по архитектуре разделов.

`esp_ota_begin/write/end` получает только target `app0` или `app1` размером 4 МиБ. LittleFS начинается с `0x820000` и не пересекается ни с одним app slot. Текущий OTA также отвергает filesystem images и oversized body.

Это не статистическая вероятность вида «99%»: штатный app OTA вообще не выполняет запись в LittleFS. Физическая неисправность Flash всегда возможна, но не является обычным результатом OTA.

### Матрица сценариев

| Сценарий | Результат для custom assets |
|---|---|
| обычный app-only web OTA, partition table прежняя | должны сохраниться всегда |
| несколько последовательных app-only OTA | должны сохраниться всегда |
| USB upload app/bootloader с прежней таблицей без erase-all | обычно сохранятся, но это не основной контракт |
| запись factory image без полного erase и с той же таблицей | физически LittleFS не входит в текущую длину factory, но полагаться на это как на recovery-контракт не следует |
| `erase_flash` / действительно чистая factory installation | будут удалены, вероятность сохранения 0% |
| `uploadfs` или отдельная запись в `0x820000` | будут перезаписаны |
| будущая смена offset/размера partition table | нужна отдельная миграция; без неё сохранность не обещается |
| потеря питания во время asset upload при A/B схеме | прежний активный asset должен сохраниться |
| потеря питания при простой перезаписи одного файла | возможна потеря custom asset, поэтому вариант запрещён |
| CRC/mount error | встроенный default, без падения UI |

Флаг активности хранится в versioned manifest рядом с ресурсами, поэтому сброс NVS не превращает исправные файлы в неизвестное состояние. Принятая политика 0.3.9: обычный factory reset очищает настройки, trip/journal и калибровки, но сохраняет custom assets; фон и логотип удаляются отдельными явно подтверждаемыми кнопками web UI.

## Отказоустойчивость

На каждом старте:

1. попытаться безопасно смонтировать LittleFS;
2. выбрать последний valid manifest generation;
3. проверить тип, размеры, length и CRC;
4. загрузить custom asset;
5. при любой ошибке записать причину в log/status и использовать embedded default;
6. никогда не оставлять экран пустым из-за повреждения пользовательского файла.

Встроенные `drawCarbonBackground()` и `kHavalLogoRgb565` удалять нельзя. Они являются recovery path и работают даже при полностью пустом/повреждённом LittleFS.

## Реализованное решение 0.3.9

- browser-side decode/crop/resize/darken/RGB565 LE conversion и CRC32;
- background строго 240×240 / 115 200 байт;
- logo пропорционально вписывается максимум в 220×80;
- A/B files + A/B versioned manifest + CRC32 + read-back;
- raw-body upload без multipart, точный `Content-Length`, idle/absolute deadline;
- load once into PSRAM/current startup cache;
- embedded defaults always available;
- no auto-format для непустого mount failure;
- отдельные enable/fallback/delete controls и REST status.

Код: `include/asset_store.h`, `src/asset_store.cpp`, `src/dashboard_ui.cpp`,
`src/service_portal.cpp`, `web/index.html`. Host recovery coverage находится в
`tests/host/storage_recovery_tests.cpp`, browser conversion/transport coverage —
в `tests/web/brightness_ui.cjs`.

## Матрица проверки

Программно проверяются:

1. точные dimensions/byte counts и CRC browser payload;
2. raw headers/body, preflight и final verified response;
3. corrupted header/CRC/length → embedded fallback;
4. A/B upload, manifest read-back и сохранение предыдущего банка до commit;
5. повреждение одного типа ресурса не блокирует обновление другого;
6. enable/disable/delete и выбранная factory-reset policy;
7. multipart запрещён, TWDT не отключается;
8. ресурсы находятся вне app image и boot-selection path.

Остаются обязательными на физическом N16R8:

1. upload background/logo, reboot и визуальное сравнение preview с GC9A01;
2. реальные power cuts на стадиях A/B update;
3. app0→app1, app1→app0 и rollback с проверкой сохранности assets;
4. PSRAM failure/fallback и benchmark render до/после.
