# H2 Gauge 0.4.2-diag4 — пассивное наблюдение + контролируемый single-shot тест

**Дата сборки:** 2026-10-08

**Цель:** ESP32-S3 DevKitC-1 N16R8 (`esp32s3-n16r8`)

**Назначение:** отделить неисправность физического TX-пути (GPIO16/CTX, SN65HVD230, питание/земля, терминация) от конфликта одинаковых функциональных идентификаторов `0x7DF` (H2 Gauge и внешний OBD-мастер, главный кандидат — BRC S32 Evo)

**ID зонда:** `0.4.2-diag4-fix2` (виден в строке состояния страницы как `· оверлей 0.4.2-diag4-fix2`)

**Официальный release:** `0.4.2` в каталоге [`../../releases`](../../releases) не заменён и не изменён

`0.4.2-diag4` заменяет диагностические `diag3`/`diag2`/`diag1` для CAN-проверки. Diag3 и её артефакты остаются без изменений. Diag4 использует оверлей diag3 как базу (valve-authoritative индикация топлива, диагностическая web-страница, GPIO/TWAI/кадры) и добавляет к нему:

1. **полное отключение автоматической передачи** — ни discovery, ни polling, ни Mode 22, ни DTC-запросы не отправляются; H2 в service mode только принимает CAN;
2. **безопасный физический TX-тест по кнопке** — до трёх отдельных single-shot запросов `0x7E0 02 01 0C 00 00 00 00 00` с окном ответа 500 мс и паузой 2 с между попытками;
3. **пословный журнал попыток** — TX success/fail, TEC/REC, дельты bus error, arbitration lost, TX failed, RX missed/overrun и полученный ответ;
4. **DTC scan/clear заблокированы** (HTTP 409) на время работы диагностического образа.

## Что исправлено после полевого запуска 2026-10-08

Первый образ diag4 (`242bc33c…`) **не отправил ни одного кадра**. На странице это выглядело так: «Тест 0x7E0 → 0x7E8» показывал «выполняется (retry_delay)», «Попытки 0 из 3 (повторов: 0)», прошло 45.6 с, затем 164.7 с; в TWAI controller — `running`, `TEC/REC 0/0`, `TX failed 0`, `bus errors 0`, `arb lost 0`, очереди `0/0`, «Последний TX: нет»; «Ответы вне окна 0»; пассивный счётчик «TX retained (наш) 0». То есть тест бесконечно «выполнялся», не передав ничего.

Причина: единственный вызов `pump()` (отправка кадра попытки) стоял в **непрерывной** ветке `obd_client.cpp::loop()`, а в diag4 клиент всегда в состоянии TX-paused (`diagnosticTxPaused_ = true`, потому что автоматический опрос выключен) → эта ветка не выполнялась никогда. Пассивное наблюдение при этом работало, поэтому счётчики выглядели здоровыми.

**fix1** (коммит `a962435`):

1. `pump()` вместе с `monitor_.record()` перенесён внутрь ветки `if (diagnosticTxPaused_)`, сразу после `singleShot_.tickPassive(now)`;
2. `tickPassive()` получил стартовый watchdog `kStartWatchdogMs = 3000` мс: если через 3 с после старта не отправлено ни одной попытки, прогон останавливается с `StopReason::Watchdog` и `lastError = "probe_not_scheduled"` — вместо бесконечного «выполняется»;
3. страница и `/api/diagnostics/hardware` показывают честное состояние: `obd.softwareTxPaused` и `obd.automaticRequests` (`disabled`/`active`) вместо ложного красного «ACTIVE — ОШИБКА diag4», плюс ID зонда в строке состояния и baseline-строки TEC/REC и ArbLost/BusErr.

**fix2** (коммиты `1c0be59`, `5c5508e`): ответ `negative_response` теперь распознаётся по стандарту SAE J1979/ISO 15765 — `03 7F 01 <NRC>` (сервис 0x7F, исходный сервис 0x01, код отказа; **PID не повторяется в ответе**). Прежнее правило требовало `data[2] == 0x0C`, поэтому реальный отказ ECU выглядел как `no_response` и сжигал весь бюджет попыток, не объясняя причину. Сейчас такой кадр останавливает прогон с `negative_response` (это тоже доказательство, что ECU разобрал наш физический кадр), а `7F <другой сервис>` (например, отказ на Mode 02 из чужого трафика BRC) игнорируется.

Плюс к этому колонка **Alerts** теперь читает `rxMissedDelta` напрямую (раньше поле подменялось на месте вызова через `Object.assign`, из-за чего переименование в JSON молча обнулило бы колонку) и дополнительно показывает `rx_overrun`. Статический гейт проверяет контракт целиком: все поля вида `a.<поле>`, которые читает страница, обязаны присутствовать в JSON попытки.

**Как узнать, что прошит старый образ:** в строке состояния нет пометки `· оверлей …`, карточка OBD может гореть красным «ACTIVE — ОШИБКА diag4», а при нажатии теста состояние застревает в «выполняется (retry_delay)» с «Попытки 0 из 3» дольше трёх секунд. В этом случае нужно перепрошить образ из таблицы ниже.

## Почему именно так

`0.4.2-diag3` и полевые снимки показали: при обмене 5 запросов/с с таймаутом 500 мс контроллер уходил в повторяющиеся циклы ошибок (`TEC/REC` менялись `0/0 → 128/49 → 248/0 → 184/33 → 0/0`, arbitration lost до `159`, счётчик software/alert ошибок `1259 → 1567`, при этом приём и ответы `0x7E8/0x7E9` продолжались). Такой же функциональный ID `0x7DF` у H2 и у другого активного мастера означает: арбитраж не различает два разных тела кадра, ошибка бита данных плюс аппаратный авто-retry могут разгонять `TEC`. Поэтому в diag4:

- адрес запроса — **физический** `0x7E0`, он не может совпасть с чужими функциональными `0x7DF`;
- кадр помечается `ss = 1` (**single shot**): TWAI передаёт его ровно один раз и никогда не повторяет аппаратно;
- повторов максимум 3, каждый — отдельная управляемая попытка с паузой 2 с после неудачи;
- тест немедленно прекращается на первом валидном `04 41 0C` от `0x7E8`, а также при появлении дельт bus error / TX failed или росте `TEC` — то есть при первом признаке, что кадр не уходит чисто;
- никаких запросов DTC и Mode 04.

## Что изменено и что не изменено

Диагностическая сборка, как и diag3, после каждого запуска автоматически включает Wi-Fi service mode (удерживать GPIO4 не требуется). Отличие: штатный read-only OBD polling **выключен** программно, при этом приём CAN, счётчики TWAI и таблица кадров остаются активными.

Дополнительно к странице diag3:

- раздел **«Безопасный физический TX-тест»** с одной кнопкой `Тест 0x7E0 → 0x7E8`, кнопкой `Прервать тест` и таблицей попыток;
- строка `OBD / пассивный режим`: `Автоматический опрос = disabled` (если видно `ACTIVE` — установлен не тот образ);
- пассивный baseline: `passive.elapsedMs`, `passive.requiredMs`, снимок счётчиков на момент входа в service mode;
- латчированные TWAI alert flags (`tx_failed`, `arbitration_lost`, `bus_error`, `bus_off`, `bus_recovered`, `rx_queue_full`);
- ответы `0x7E8 41 0C`, пришедшие вне окна нашей попытки, отмечаются как `lateResponse` и не приписываются тесту.

Условия запуска теста (проверяются на устройстве, отказ возвращает `409` с причиной):

| Причина отказа | Значение |
| --- | --- |
| `passive_window` | прошло меньше 10 с с момента входа в service mode |
| `test_running` | предыдущий тест ещё выполняется |
| `controller_not_running` | TWAI не в состоянии `running` |
| `twai_status_unavailable` | `twai_get_status_info()` недоступен |
| `tx_queue_not_empty` | в очереди TX остался кадр от прошлой активности |
| `tx_path_not_paused` | программный TX не приостановлен. В diag4 клиент всегда TX-paused; отказ с этой причиной означает, что прошит не тот образ |

Тайминги попытки:

```text
TX  0x7E0  02 01 0C 00 00 00 00 00   (ss = 1, без аппаратного повтора)
ожидание ответа      500 мс
пауза перед повтором 2000 мс
максимум попыток     3
watchdog теста       30000 мс
стоп                 первый валидный 0x7E8 04 41 0C xx xx
```

Для каждой попытки в JSON и в таблице сохраняются:

- `txAttempted`, `txSuccess`, `txResult` (`ESP_OK`/код ошибки драйвера);
- `tecBefore → tecAfter`, `recBefore → recAfter` и дельты;
- `busErrorDelta`, `arbLostDelta`, `txFailedDelta`, `rxMissedDelta`, `rxOverrunDelta`;
- `outcome`: `valid_response` / `negative_response` (`03 7F 01 <NRC>` — отказ ECU, PID в ответе не повторяется) / `no_response` / `tx_failed` / `aborted`;
- `response`: `id`, `data`, `valid`, `latencyMs`, `rpm` (для валидного ответа).

Что diag4 **не** делает: не отправляет `0x7DF`, не сканирует DTC, не выполняет Mode 04, не поддерживает многосегментные ISO-TP ответы (для PID `0C` они не нужны).

## Установка через существующий OTA

1. Поставьте автомобиль, включите стояночный тормоз, селектор — `P`/нейтраль. Во время OTA не двигайтесь.
2. На текущей прошивке войдите в обычный service mode и подключитесь к Wi-Fi `H2-Gauge-XXXX`.
3. Откройте `http://192.168.4.1`. Если телефон уходит в мобильный интернет, временно отключите мобильные данные/VPN, но оставьте Wi-Fi H2 Gauge.
4. В разделе обновления выберите `h2-gauge-v0.4.2-diag4-esp32s3-n16r8.bin`.
5. Подтвердите OTA и дождитесь **100% и автоматической перезагрузки**. Не выключайте питание и не нажимайте `EN` во время записи.
6. После reboot заново подключитесь к `H2-Gauge-XXXX` и откройте `http://192.168.4.1`.
7. В верхней строке должно быть `0.4.2-diag4 / esp32s3-n16r8`. Если показана другая версия, диагностику не начинайте.

Главная страница `/` — диагностика. Ссылка **«Обычный интерфейс»** ведёт на `/normal`.

## Порядок полевого теста

Проверку выполняйте только на неподвижном автомобиле. При включении BRC/LPG двигатель, вероятно, должен работать; не проводите тест в закрытом помещении без безопасной вентиляции.

### 1. Пассивный baseline (H2 ничего не передаёт)

1. Включите зажигание, при необходимости запустите двигатель. Не двигайтесь.
2. Откройте `http://192.168.4.1`.
3. Оставьте страницу открытой 30–60 секунд, не нажимая тест. В это время кнопка показывает оставшееся пассивное окно, затем становится активной.
4. Зафиксируйте скриншотом: **Быстрый итог**, **OBD / пассивный режим**, **TWAI controller**, **CAN activity**, **Последние CAN кадры**.
5. Сохраните raw JSON:
   - `http://192.168.4.1/api/diagnostics/hardware`
   - `http://192.168.4.1/api/can/snapshot`
6. Сравните с прошлыми полями: `TX retained` должен быть **0** (H2 не передаёт), `RX 0x7DF` и ответы `0x7E8/0x7E9` от чужих запросов продолжаются, `RX missed/overrun` остаются `0/0`.

### 2. Один контролируемый тест

1. Убедитесь, что таблица попыток показывает **«Тест ещё не запускался»**, а кнопка `Тест 0x7E0 → 0x7E8` активна.
2. Нажмите кнопку **один раз** и дождитесь остановки теста (до ~6 секунд на три попытки). Кнопка сообщит о приёме запуска.
3. Сразу зафиксируйте скриншотами раздел **«Безопасный физический TX-тест»** (строка состояния, латчированные alerts, таблица попыток) и **TWAI controller**.
4. Сохраните оба raw JSON ещё раз. Ключевые поля: `singleShot.stopReason`, `singleShot.attempts[]` целиком.
5. Запишите отдельно: показывал ли BRC/GLO `LPG` или бензин, был ли двигатель запущен, что загоралось на панели.
6. Если нужен повторный прогон — подождите 2 секунды (короткая пассивная пауза), нажмите кнопку снова. Больше трёх попыток на запуск не бывает; при необходимости сделайте ещё один запуск и снова сохраните JSON.
7. Тест сам остановится при появлении ошибок; нажатия «Прервать тест» достаточно, если нужно остановить немедленно.

### 3. Повтор при включённом ГБО (по желанию)

Тот же один тест при включённом BRC и подтверждённом переходе на газ. Отдельно зафиксируйте раздел **LPG / PC817** (из diag3): `rawLevel`, `electricalActive`, `candidate`, `debounceSatisfied`, `stable`, `selectedFuel`, `source`.

## Как читать результат

| Результат теста | Наиболее вероятный вывод |
| --- | --- |
| `valid_response` (`0x7E8 04 41 0C …`), дельты bus error/arb lost/TEC нулевые | Физический TX-путь и драйвер работают. Проблема была в конкуренции `0x7DF` и/или аппаратном авто-повторе. Возврат на официальный 0.4.2; дальше решать вопрос единственного мастера `0x7DF` (BRC/H2) |
| `no_response` во всех 3 попытках, дельты ошибок нулевые | Кадр уходит чисто, но `0x7E0` не отвечает: ECU не отвечает на физический адрес, или ответ не доходит. Смотреть в это же время чужие пары `RX 0x7DF → 0x7E8` и `latestRx` |
| `stopReason=bus_error` / `tx_failure`, `tecAfter > tecBefore`, `busErrorDelta > 0` | Кадр не уходит физически: проверять GPIO16/CTX, SN65HVD230 (питание, земля, RS), CANH/CANL, терминацию (два по 120 Ω), длину/разводку шлейфа |
| `stopReason=arbitration_lost`-эффект (`arbLostDelta > 0`) без ответа | На шине одновременно говорит кто-то ещё; проверить, не отвечает ли кто-то на `0x7E0`, и повторить тест без BRC |
| `stopReason=controller_not_running` / `bus_off` | Контроллер потерял шину: снять оба JSON и сообщить; дальнейшие попытки не предпринимать |
| `TX failed` (`txResult != ESP_OK`) | Очередь/драйвер: снять JSON, перезагрузить, повторить один раз |
| `lateResponse` растёт, но попытки `no_response` | Ответы `41 0C` на шине есть, но они приходят вне нашего окна — то есть это ответы на чужие `0x7DF`, а не на наш `0x7E0` |
| `stopReason=negative_response`, `responseData = 03 7F 01 xx` | ECU принял наш физический кадр и отказал: TX-путь исправен, PID `0C` на этом адресе/в этом состоянии не поддерживается. `xx` — код отказа (NRC) |
| `stopReason=watchdog`, `lastError=probe_not_scheduled`, «Попытки 0 из 3» | Прошит первый образ diag4 (`242bc33c…`): кадр не отправлялся вообще. Перепрошить образ из таблицы |

Мгновенные уровни GPIO16/17 не заменяют счётчики: доказательствами являются `singleShot.attempts[]`, TWAI counters и таблица кадров.

## Что прислать для разбора

Минимальный комплект:

1. скрин «Безопасный физический TX-тест» после теста (строка состояния + таблица попыток);
2. raw JSON `http://192.168.4.1/api/diagnostics/hardware` (там `singleShot` целиком);
3. raw JSON `http://192.168.4.1/api/can/snapshot` до и после;
4. скрин пассивного baseline (§1) и строка `TWAI controller`;
5. отдельно словами: ГБО включено/выключено, двигатель запущен/нет, кнопка BRC, были ли подключены другие сканеры/ELM;
6. версии обоих OTA-слотов из «Обычный интерфейс».

## Возврат на официальный 0.4.2

После завершения диагностики:

1. откройте `http://192.168.4.1/normal`;
2. в OTA выберите официальный `releases/h2-gauge-v0.4.2-esp32s3-n16r8.bin`;
3. дождитесь проверки и автоматического reboot;
4. подтвердите в service UI текущую сборку `0.4.2` и версии обоих OTA-слотов.

Не используйте factory image для возврата через web OTA. App-only переход сохраняет NVS, настройки, trip, калибровки, DTC history, LittleFS journal и пользовательские ресурсы.

## Файлы разработки

- `hardware-diagnostics.patch` — изолированный оверлей против нетронутого дерева `0.4.2` (включает базу diag3 и изменения diag4); production source `0.4.2` не содержит diagnostic code;
- `hardware-diagnostics.html` и `hardware_diagnostics_gz.h` — исходная и встроенная (gzip, `mtime = 0`) страницы;
- `../../tools/build_hardware_diagnostics.py` — воспроизводимая сборка app image: экспорт чистого дерева `HEAD` через `git archive`, применение патча, `pio run -e esp32s3_n16r8_diag`, проверка manifest, копирование результата;
- `../../tools/check_hardware_diagnostics.py` — static/gzip isolation gate: патч применяется к чистому дереву, gzip-файл соответствует HTML, патч не трогает release окружение `[env:esp32s3_n16r8]`, в диагностическом образе верный manifest и присутствуют маркеры diag4, в release-образе маркеров нет.
